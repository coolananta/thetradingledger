# Migrating from Quarto to Hugo — what actually happened, and what's left for you

This project was built and **test-compiled with the real Hugo Extended binary**
(v0.139.4) before being handed to you — it's not a guess at what should work, it's
a build that already succeeded, with the output inspected line-by-line to confirm
callouts, stat-boxes, decision trees, forms, and analytics all survived intact.

## What you need installed

**Hugo Extended**, not plain Hugo — the SCSS pipeline (`css.Sass`) requires the
extended build or `hugo --gc --minify` will fail immediately.
Install: https://gohugo.io/installation/ (or `brew install hugo` on macOS, which
installs the extended version by default).

## Previewing locally

```bash
hugo server
```
Open the printed localhost URL. Live-reloads as you edit.

## Publishing to Netlify

Unlike Quarto, there's no `hugo publish netlify` one-liner. Two real options:

**Option A — git-based (recommended for Hugo specifically):**
Push this project to a GitHub repo, then in Netlify: "Add new site" → "Import an
existing project" → pick the repo. Netlify auto-detects Hugo and uses the
`netlify.toml` in this project (build command `hugo --gc --minify`, publish
directory `public`). Every future `git push` auto-deploys.

**Option B — CLI, closer to your old workflow:**
```bash
npm install -g netlify-cli
netlify login
hugo --gc --minify
netlify deploy --prod --dir=public
```
The first `netlify deploy` (without `--prod`) will ask you to link to your
existing `tradingzournal` site or create a new one — **pick "link to existing
site"** to avoid the exact duplicate-site issue you hit before with `quarto
publish`.

## What required real conversion (not just syntax swaps)

- **Quarto callouts** (`::: {.callout-note}`) → a hand-written shortcode:
  `{{< callout type="note" title="..." >}}...{{< /callout >}}`. All existing
  callouts across all posts were converted already.
- **Raw HTML** (your stat-box/tree/timeline/bar-chart divs) required setting
  `unsafe = true` in `hugo.toml`'s Goldmark config — without it, Hugo strips
  raw HTML by default and all of that content would silently vanish.
- **The mermaid diagram** in the HYFM/EZRA post was manually rebuilt using your
  existing `.tree` component instead of adding mermaid.js — keeps the zero-JS
  posture instead of trading it away for one diagram.
- **Python code chunks** (HYFM/EZRA and AMIX posts) — Hugo cannot execute code.
  I actually ran the real Python for you and:
  - Converted the AMIX extension table and the HYFM/EZRA comparison table into
    plain static Markdown tables.
  - Generated one real matplotlib chart as a static PNG
    (`static/images/hyfm-ezra-extension-chart.png`) and embedded it as a normal
    image.
  - **Removed** the HYFM/EZRA "weekly cumulative P&L" chart entirely, rather
    than freezing fake placeholder data as if it were real — that chunk only
    ever had 2 of 6 days filled in. A callout at the top of that post explains
    why it's gone.
  - Three chunks that only printed values already restated in the surrounding
    prose (float rotation math, leg math, confluence math on the AMIX post)
    were deleted outright — nothing of substance was lost.

## If you want Python/R-generated charts in future posts

Hugo still can't execute code — that's a permanent property of the tool, not
a setup gap. The realistic workflow going forward: write the post as a `.qmd`
file, run `quarto render mypost.qmd --to gfm` to get the code executed and
charts exported as images, then move the resulting Markdown + images into this
Hugo project's `content/posts/` and `static/images/`. Two tools, one extra
step — not automatic the way it was inside Quarto itself.
